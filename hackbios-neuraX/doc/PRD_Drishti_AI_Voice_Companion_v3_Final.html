PRD: Drishti — AI Voice Companion for the Visually Impaired

An assistive smart glasses system coupling lightweight eyewear capture with edge reflex detection and conversational intelligence.

Problem Statement: PS-05 Status: Draft v3 — Final Form Factor: Smart Sunglasses (<38g) Build Target: Hackathon MVP + Production Roadmap

0. Summary of Decisions

  • Architecture & Product Integration: Drishti is integrated into Smart Sunglasses (<38g frame housing the camera, dual MEMS mic, and directional open-ear micro-speakers over the tragus). The sunglasses connect wirelessly over Wi-Fi SoftAP to the compute host. In the hackathon validation MVP, a laptop acts as the local testbed brain (running YOLOv8n + face_recognition + audio output); in production, this runs on the user's Android phone.
  • Dual-Tier Reliability: A local-only pipeline is the non-negotiable guaranteed base. LiveKit conversational voice (STT → LLM → TTS) is a gated stretch layer added only if early proof-of-concept tests succeed.
  • Operational Modes: Navigation Mode (proactive obstacle/hazard alerts) + Assistant Mode (on-demand conversational Q&A, scene understanding, face recognition), switched via a physical button (primary) or voice command (secondary).
  • Known-People Repo Check: The existing agent-starter-embed repo uses Pipecat + Daily.co, not LiveKit. Decision: keep LiveKit as planned; the Pipecat repo remains available as a proven fallback if LiveKit setup stalls.
  • Feasibility Review Outcomes: ESP32-CAM requires an external FTDI programmer (no onboard USB); GPIO pin choice for the mode button matters (avoid GPIO16/0/4 and SD-card pins); face_recognition/dlib often fails on Windows; YOLOv8 is AGPL-3.0 licensed; and LiveKit's real-world roundtrip latency is commonly 1.4–1.7s. All constraints are accommodated in the phased roadmap.

1. Overview

Drishti is a wearable assistive system designed as Smart Sunglasses housing an ESP32-S3 / ESP32-CAM camera node, dual microphones, and open-ear speakers, paired over wireless SoftAP with a local computer vision pipeline (YOLOv8n + face_recognition) and directional audio output.

A local-only pipeline is the guaranteed base; an internet-connected LiveKit-powered conversational voice layer is a gated stretch enhancement.

2. Problem Statement

Visually impaired individuals face two related challenges navigating unfamiliar environments:

  1. Reactive hazard awareness: Knowing what is physically in their path before bodily contact (low branches, vehicles, open drains, curbs).
  2. Situational understanding: Knowing who/what is around them on demand (reading signs, identifying people, describing seating layouts).

Drishti addresses both using local computer vision with an optional conversational AI layer.

3. Target User

  • Primary: Visually impaired individuals navigating semi-familiar indoor and outdoor environments hands-free.
  • Secondary: Caregivers and family members who pre-register familiar faces and safety contacts.

4. Goals & Success Metrics (Hackathon Demo)

Goal Success Criteria
Real-time obstacle awareness System announces a new close obstacle/person within a few seconds — exact threshold set after POC 1 timing.
Known-person recognition Correctly distinguishes 2–3 pre-registered faces from strangers under actual demo lighting (POC 3).
Usable mode switching Button press reliably cycles mode with spoken audio confirmation.
Guaranteed live demo The local-only stack runs live without any internet dependency as the non-negotiable fallback.
Stretch: conversational Q&A If POC 2 succeeds, user can ask a question and get a spoken answer via LiveKit.

5. Scope

MUST BUILD (Local-Only, Zero Internet Dependency)

  • Smart Sunglasses camera node → Wi-Fi → laptop frame pipeline (fallback: laptop webcam directly if POC 1 fails).
  • YOLOv8n (COCO pretrained) for obstacles, objects, and pedestrians, running locally on CPU.
  • Near / medium / far proximity from bounding-box size coverage (empirical distance mapping).
  • Local TTS (pyttsx3 / gTTS) — zero cloud dependency.
  • Physical push-button mode switch (Navigation ↔ Assistant) wired to a non-shared GPIO pin (13, 14, or 15 — avoiding GPIO16, 0, 4, and SD-card pins).

SHOULD BUILD — Gated Stretch Layer (Only After MUST BUILD is Stable)

  • LiveKit Agents voice pipeline (STT → LLM → TTS) for conversational Assistant-mode Q&A — gated behind POC 2.
  • Face recognition (face_recognition / dlib) for known vs. unknown people — gated behind POC 3.
  • Voice-command mode switching as a secondary input to the physical button.

Explicitly Out of Scope (12-Hour Build Window)

  • Full edge text OCR reading (deferred to Phase 2 mobile integration).
  • True standalone glasses compute without external host (deferred to Phase 4).
  • Haptic vibration motors.
  • Precise step-calibration distance metrics.
  • Multi-person tracking and biometric re-identification.

7. User Experience & Interaction Flows

Navigation Mode (Default)

  • Continuous obstacle scanning at 5–10 fps.
  • Proximity alerts: Speaks object name and direction when bounding box exceeds threshold (e.g. "Chair, close ahead", "Person approaching, 12 o'clock").
  • Cooldown / Anti-spam: Suppresses repeated alerts for the same stationary object within 3 seconds.

Assistant Mode

  • Continuous scanning is throttled to conserve compute and audio bandwidth.
  • User triggers query via button or push-to-talk voice prompt.
  • LiveKit STT → LLM → TTS composes an answer from live detection context.
  • Known-face names surface here if face recognition passes; otherwise reports generic "a person is here."

8. Technology Stack

Layer Choice Engineering Note
Capture Hardware Smart Sunglasses with ESP32-CAM (Fallback: Laptop Webcam) Requires external FTDI/USB-TTL programmer to flash — no built-in USB port.
Communications Wi-Fi 802.11 b/g/n (SoftAP / Local Hotspot) Verify achievable fps on venue network in POC 1 before committing.
Object Detection YOLOv8n (Ultralytics, COCO Pretrained) AGPL-3.0 licensed — fine for hackathon demo; commercial product requires enterprise license.
Face Recognition (Stretch) face_recognition (dlib) Officially Mac/Linux; Windows dlib compile requires CMake/Visual Studio build tools — test dev machine first.
Local Audio (MUST BUILD) pyttsx3 or gTTS Zero internet dependency, zero API cost.
Voice Agent (Stretch) LiveKit Agents (STT + LLM + TTS) Requires LiveKit server and API keys; published roundtrip latency is commonly 1.4–1.7s.
Voice Fallback Reference Pipecat + Daily.co (agent-starter-embed) Kept on hand as tested fallback if LiveKit setup stalls.
Core Runtime Python 3.10+ Cross-platform coordinator.

9. Hardware Checklist

  • Smart Sunglasses Frame: TR90 eyewear frame housing ESP32-CAM module, OV2640 lens, and open-ear speaker for hands-free eye-level capture.
  • FTDI / USB-TTL Programmer: Required to flash code to the ESP32-CAM module.
  • Push Button: Wired to a confirmed-safe GPIO pin (13, 14, or 15 — not 16, 0, 4, or SD-card pins).
  • Portable Power Bank: Powers ESP32-CAM via 5V rail.
  • Host Laptop: Runs YOLOv8n, local TTS, and optional LiveKit agent.
  • Microphone: Built-in laptop mic or external headset for Assistant-mode voice queries.
  • Audio Output: Open-ear directional speaker or wireless earbuds.

12. Critical Risks & Fallbacks

  • LiveKit Voice Agent: If setup or latency fails → Fall back to Local TTS only with canned phrases (or Pipecat repo).
  • face_recognition (dlib): If installation fails → Fall back to generic "person detected" from YOLO.
  • ESP32-CAM Wi-Fi Streaming: If venue network is unstable → Fall back to Laptop Webcam directly.
  • Venue Internet: If completely down → Local-only stack operates 100% offline with zero cloud dependency.

13. Risks & Mitigations

Risk Mitigation Strategy
Wi-Fi latency/instability between ESP32 and laptop Use dedicated mobile hotspot; reduce resolution to $320 imes240$; laptop webcam fallback.
LiveKit + LLM latency overrun Gate behind POC 2; treat as stretch; Pipecat/Daily.co repo as tested backup.
dlib / face_recognition install failure on Windows Test on actual dev machine before committing; generic person fallback.
Missing FTDI programmer Acquire prior to hackathon — no in-hackathon workaround for bare ESP32-CAM.
Integration time overrun Build and test each piece independently (POCs); preserve local-only fallback.

14. Path to a Real Product (Post-Hackathon)

The hackathon build is a validated MVP, not a production system. The production roadmap spans 4 distinct phases:

Phase 1 — Hackathon MVP (This PRD)

Smart sunglasses camera node + laptop brain, local-only fallback guaranteed, LiveKit as a gated stretch. Goal: prove concept viability hands-free.

Phase 2 — Mobile Prototype (Android / iOS)

  • Re-export YOLOv8n to TFLite (Android) / CoreML (iOS) and validate on-device inference speed on actual smartphone NPUs/CPUs.
  • Replace face_recognition/dlib with Google ML Kit face detection and on-device MobileFaceNet embedding models.
  • Replace local TTS with native Android TextToSpeech and iOS AVSpeechSynthesizer.
  • Replace hardcoded Wi-Fi credentials with BLE provisioning or Wi-Fi SoftAP direct pairing.
  • Deploy LiveKit's native Android (Kotlin) SDK as implemented in the hackbios-neuraX mobile client.

Phase 3 — Pilot with Real Users

  • Conduct field trials with blind and visually impaired users in authentic urban pedestrian settings over multiple weeks.
  • Measure false negatives and false positives — missed obstacles are safety hazards, not software bugs.
  • Gather empirical data on frame weight, battery endurance, and thermal dissipation on skin.

Phase 4 — Scaled Production

  • Transition to custom rigid-flex 4-layer PCB inside custom TR90 sunglasses frames (BOM: $10.92 / ₹1,056.73).
  • Undergo privacy and regulatory review for camera capture and bystander data protection.
  • Align retail pricing (₹3,999) with India's ADIP scheme for 100% government-subsidized distribution.
